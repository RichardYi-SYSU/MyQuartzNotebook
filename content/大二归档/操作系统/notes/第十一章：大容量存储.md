
# 磁盘IO传输时间

> 先找磁道，再等扇区转过来，最后读数据。

$$T_a=T_s+\frac{1}{2r}+\frac{b}{rN}$$

$T_s$代表寻道时间，磁头要移动到目标数据所在的磁道

$\frac{1}{2r}$代表平均旋转延时，磁头到达目标磁道后，目标扇区不一定刚好转到磁头下面。磁盘还要继续旋转，直到目标数据转到磁头下方。

设磁盘转速为：

$$r \text{ 转/秒}$$

那么磁盘转一圈需要：
$$\frac{1}{r} \text{ 秒}
$$
  
最理想情况：目标扇区刚好在磁头下面，等待时间是 0。

最差情况：目标扇区刚刚转过去，要等几乎一整圈，等待时间接近：
$$\frac{1}{r}$$
平均来看，目标扇区随机分布，所以平均要等半圈：
$$\frac{1}{2} \cdot \frac{1}{r} = \frac{1}{2r}
$$
则其为平均旋转延迟


$\frac{b}{rN}$代表数据传送时间，当目标数据转到磁头下方后硬盘开始传输数据

b为要传输的数据量，转速为r，每秒转r圈，N为一个磁道上一圈存放的数据量

因此传输b大小数据需要的时间是$\frac{b}{rN}$

# 磁盘调度算法

## FIFO

磁盘请求按到达顺序排队，谁先来就先服务谁，不管磁头现在在哪

[[操作系统/materials/2026-OS-CH-11-大容量存储.pdf#page=20|2026-OS-CH-11-大容量存储, 页面 20]] 折线为磁头移动轨迹，纵轴为磁道号

计算磁头移动距离是就是把相邻两次访问的磁道差取绝对值

## PRI

其目标和其余算法不同，不是让磁头移动距离最短或吞吐率最高，而是为了满足比如提高交互式程序响应速度等目标

比如：

|**请求来源**|**请求磁道**|**优先级**|
|---|---|---|
|交互式程序|55|高|
|数据库后台任务|160|低|
|批处理任务|90|中|
|系统关键进程|38|高|
PRI 调度不会简单地按照：
$$55 \rightarrow 160 \rightarrow 90 \rightarrow 38$$
也不会一定选择离当前磁头最近的请求。

它会优先考虑优先级，比如先处理高优先级请求：
$$55 \rightarrow 38 \rightarrow 90 \rightarrow 160$$
**缺点** 容易导致饥饿，长作业、低优先级作业可能一直等不到磁盘服务

## SSTF

Shortest Service Time First 每次都选择距离当前磁头位置最近的磁盘请求来处理

优点是每次都选择最近请求，平均寻道时间通常比FIFO小，磁盘效率更高

缺点是可能导致远处请求长期等待，出现饥饿

## SCAN

也叫电梯算法，类比电梯运行：电梯先沿一个方向运行，途中把这个方向上遇到的所有请求都处理完；到达一端后，再反向运行，处理反方向上的请求。

**磁头先沿一个方向移动，依次服务该方向上的磁道请求；到达磁盘一端或该方向最后一个请求后，再反向移动，继续服务另一边的请求。**

优点是比较公平，不会像SSTF那样一直照顾离当前磁头最近的请求，导致远处请求长期等待

靠近磁盘两端的请求可能会更快被服务（偏向最内侧和最外侧磁道的请求）

## C-SCAN

只按一个方向服务，磁头只在一个方向上处理请求。到达磁盘一端后，直接“跳回”另一端，然后继续按同一个方向扫描。

比 SCAN 更公平，因为所有请求基本都按照同一个方向被扫描到，等待时间更均匀。

## N步SCAN

把磁盘请求队列按固定长度 N 分成若干小队列，每次只处理其中一个小队列，并且在这个小队列内部使用 SCAN 算法。

普通 SCAN 基础上的改进，主要目的是避免某些请求长期等待，尤其是避免“磁臂黏着”现象。

假设 N = 4，磁盘请求序列是：
$$55,\ 58,\ 39,\ 18,\ 90,\ 160,\ 150,\ 38,\ 184$$
把它按每组 4 个请求划分：
$$Q_1 = \{55, 58, 39, 18\}$$
$$Q_2 = \{90, 160, 150, 38\}$$
$$Q_3 = \{184\}$$
然后系统一次只处理一个子队列。

## FSCAN(FrozenSCAN)

分布冻结扫描策略，SCAN的双队列改进版

当前这一轮扫描只处理“旧请求”；扫描过程中来的“新请求”先放到另一个队列里，等下一轮再处理

普通 SCAN 的问题是：  
磁头在扫描过程中，新请求可能不断插入当前队列。如果新请求很多，当前扫描队列会不断变化，可能导致某些原本的请求等待时间变长。

FSCAN 的解决方法是使用 **两个子队列**：$Q_1,\ Q_2$

假设开始时：

$$Q_1 = 当前已有请求$$
$$Q_2 = 空$$
系统用 SCAN 算法处理 $Q_1$。在处理 $Q_1$的过程中，所有新来的请求都不加入 $Q_1$，而是加入 $Q_2$。

等 $Q_1$ 全部处理完之后，再交换两个队列：

$$Q_2 \rightarrow 当前处理队列$$
$$Q_1 \rightarrow 新请求等待队列$$
然后继续下一轮扫描。

提高公平性

## Linux截止时间调度器

**Deadline 调度器 = LBA 顺序队列 + FIFO 截止时间队列。**

它既想要：
$$\text{按磁盘地址顺序处理，提高效率}$$
又想要：
$$\text{给请求设置截止时间，避免饥饿}$$
所以它不是单纯的 FCFS，也不是单纯的 SCAN，而是在 **顺序访问效率** 和 **等待时间公平性** 之间做折中

## NVM调度

> 适用于非HDD，如SSD等

|**设备类型**|**主要瓶颈**|**调度重点**|
|---|---|---|
|机械硬盘 HDD|磁头寻道、旋转延迟|排序请求，减少磁头移动|
|SSD / NVMe / NVM|并发、队列、写放大、调度开销|简化调度，合并请求，提高吞吐|
### 合并相邻LBA请求

比如有几个写请求：
$$100,\ 101,\ 102,\ 103$$
如果它们是相邻的，调度器可以把它们合并成一个较大的 I/O 请求：
$$100 \sim 103$$
这样可以减少 I/O 请求数量，提高吞吐量。

### 控制请求队列

NVMe 设备支持很深的队列和大量并发请求。  
它的重点不是“磁头怎么走”，而是：如何把大量请求高效地提交给设备

比如课件里提到：

使用 NVM 时，每秒输入/输出操作数 IOPS 要高得多

机械硬盘可能只有几百 IOPS，而 NVMe SSD 可以达到几十万甚至更高。所以调度器不能太复杂，否则调度器本身会成为性能瓶颈。

### 避免写放大

SSD 写入并不是简单覆盖原位置。它通常涉及：
$$\text{写入新页} \rightarrow \text{标记旧页无效} \rightarrow \text{垃圾回收} \rightarrow \text{擦除块}$$

如果系统产生很多零散小写入，SSD 内部可能需要搬移大量有效数据，导致实际写入量大于用户请求写入量，这就是 **写放大**。

例如用户只写了：4KB

但 SSD 内部为了擦除、搬移、重写，可能实际写了：16KB, 32KB

这会降低性能，也会影响 SSD 寿命。

# 存储设备管理

## 文件与硬盘IO

硬盘IO在块中完成，文件IO在簇中完成，簇包含多个块

|**对比项**|**文件 I/O**|**磁盘 I/O**|
|---|---|---|
|视角|应用程序 / 文件系统|块设备 / 磁盘控制器|
|操作对象|文件|磁盘块、扇区、LBA|
|典型单位|字节、文件偏移、簇|扇区、块|
|是否理解文件名|理解|不理解|
|例子|读 /home/a.txt|读 LBA 2048|

程序执行：

```c
read(fd, buf, 100);
```

意思是读取某个文件的 100 字节。

这属于 **文件 I/O**。

但磁盘不能直接理解“读取这个文件的 100 字节”。操作系统要通过文件系统找到这个文件对应的磁盘位置，比如：

LBA 8000

然后向磁盘发出请求：

读取 LBA 8000

这属于 **磁盘 I/O**。

文件 I/O 是“对文件读写”，磁盘 I/O 是“对磁盘块读写”。文件 I/O 最终通常会被文件系统转换成一个或多个磁盘 I/O。

## 文件系统与操作系统

[[操作系统/materials/2026-OS-CH-11-大容量存储.pdf#page=31|2026-OS-CH-11-大容量存储, 页面 31]] 操作系统提供整体资源管理能力，而文件系统专门负责存储设备上的文件组织、目录、权限、空间分配等问题

| **分区**     | **内容**                |
| ---------- | --------------------- |
| / 根分区      | 当前 Linux 系统           |
| / home 分区  | 用户文件                  |
| Windows 分区 | Windows 系统和 NTFS 文件系统 |
| swap 分区    | 交换空间                  |
| 原始分区       | 不格式化成文件系统，直接给数据库等程序使用 |
这里的“文件系统”有两层含义：

第一，**文件系统是一种磁盘数据组织格式**。

例如：
$$ext4,\ xfs,\ btrfs,\ NTFS,\ FAT32$$
这些文件系统规定了磁盘上如何保存：

文件内容、目录结构、文件名、权限、时间戳、空闲空间信息

第二，**文件系统也是操作系统内核中的一套管理模块**。

操作系统需要有对应的文件系统驱动，才能识别并访问这些格式。

比如 Linux 要访问 ext4 分区，就需要 ext4 文件系统模块；要访问 NTFS 分区，就需要 NTFS 相关驱动。

[[操作系统/materials/2026-OS-CH-11-大容量存储.pdf#page=36|2026-OS-CH-11-大容量存储, 页面 36]] 这里为什么有单独的存储网络和通信网络？

普通通信网络负责主机之间的数据通信；存储网络负责服务器和存储设备之间的块级 I/O。二者分开，可以提高性能、降低干扰、增强可靠性，并方便集中管理大规模存储。

# RAID

使用多个磁盘来创建一个更大更快更可靠的磁盘的错觉

RAID的内部是一个计算机系统：

- 专用CPU+软件管理的磁盘
- RAM和非易失性存储器
- 多种不同的配置选项

![[../assets/RAID.png]]

## RAID 0

| **特点** | **RAID 0**   |
| ------ | ------------ |
| 数据分布方式 | 块级条带化分布到多块磁盘 |
| 读写性能   | 高            |
| 存储利用率  | 100%         |
| 是否有冗余  | 没有           |
| 是否能容错  | 不能           |
| 任意一盘损坏 | 整个阵列数据可能丢失   |

图中有 4 块磁盘，数据条带按顺序分布：
$$strip\ 0 \rightarrow 磁盘1$$
$$strip\ 1 \rightarrow 磁盘2$$
$$strip\ 2 \rightarrow 磁盘3$$
$$strip\ 3 \rightarrow 磁盘4$$

然后继续循环：
$$strip\ 4 \rightarrow 磁盘1$$
$$strip\ 5 \rightarrow 磁盘2$$
$$strip\ 6 \rightarrow 磁盘3$$
$$strip\ 7 \rightarrow 磁盘4$$
所以它把连续的数据分散到了多块磁盘上。

## RAID 1

核心是镜像，把同一份数据完整地复制到另一块磁盘上

使用条带化

|**特点**|**RAID 1**|
|---|---|
|实现方式|镜像，把数据复制到另一块盘|
|是否有冗余|有|
|容错能力|可以容忍镜像组中一块盘损坏|
|读性能|可能提升|
|写性能|通常不提升，需要写两份|
|容量利用率|约 50%|
|主要缺点|成本高|

## RAID 2

位级条带，比RAID 0 的条带更细，通过海明码来提供错误检测和纠错能力

现在很少使用，因为现代磁盘已有ECC纠错机制，内部已经能处理很多位错误，RAID 2 再使用海明码，成本高、实现复杂、收益不明显

## RAID 3

最少需要三块磁盘，因为要包含：
$$\text{至少 2 块数据盘} + \text{1 块专用校验盘}$$
也就是：$2 + 1 = 3$

核心是：字节级条带化 + 一块专用奇偶校验盘

## RAID 4

块级条带化+一块专用奇偶校验盘

右边灰色的是 **专用校验盘**。

对于每一组横向对应的数据块，会计算一个奇偶校验块：
$$P(0-3) = block0 \oplus block1 \oplus block2 \oplus block3
$$
可容忍一块磁盘故障，与RAID 3 的区别主要是条带粒度不同

|**对比**|**RAID 3**|**RAID 4**|
|---|---|---|
|条带化粒度|位级/字节级小条带|块级条带|
|访问方式|并行访问，多个盘一起参与|独立访问，不同块可单独读|
|校验盘|专用校验盘|专用校验盘|
|适合场景|大块连续传输|支持更多独立小读请求|

专用校验盘会成为写入的瓶颈，因为所有写操作都需要更新校验盘

小写入代价高

## RAID 5

与RAID 4 类似，但是校验位分散到了各个盘中，能够优化RAID 4中专用校验盘的写入瓶颈，使用轮转分布

仍为异或校验方式

## RAID 6

可靠性更高，因为有两个校验位，能够容许两块磁盘出错

RAID 5 的增强版，数据条带化+2份分布式校验

牺牲两块盘容量用于校验

## Solaris ZFS

**ZFS 把卷管理和文件系统结合起来，用统一的存储池管理底层磁盘。**

它不像传统系统那样先做 volume，再在 volume 上建 FS；而是直接让 ZFS 管理一组磁盘，并在其上创建多个文件系统。
