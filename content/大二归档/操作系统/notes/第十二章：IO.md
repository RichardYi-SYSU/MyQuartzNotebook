
# 相关概念

- 端口：设备的连接点
- 总线：一组线路和通过线路传输信息的严格定义的一个协议：
	- PCI总线：比如PCI Express
	- 扩展总线连接相对较慢的设备
	- 串行连接SCSI公共磁盘接口
- IO控制器：可以操作端口、总线和设备的一组电子器件，包含处理器、微码、专用存储器、总线控制器等
- 设备控制器：CPU与IO设备之间的接口，向CPU提供特殊指令和寄存器
- IO地址：CPU用来控制IO硬件
- 内存映射IO：设备的寄存器/存储被映射到内存物理地址空间中，通过load/store完成IO操作，MMU设置映射

# 轮询

 [[操作系统/materials/2026-OS-CH-12-IO系统.pdf#page=17|2026-OS-CH-12-IO系统, 页面 17]]

**1. 轮询的核心思想**

I/O 设备通常比 CPU 慢很多，比如键盘、打印机、磁盘、串口等。

所以 CPU 给设备发出读/写命令后，设备不能马上完成。于是设备控制器中通常会有几个状态位：

- **忙位 Busy**：设备是否正在工作
- **就绪位 Ready**：设备是否准备好
- **错误位 Error**：操作是否出错
- **命令准备位 Command Ready**：CPU 的命令是否已经准备好

轮询就是 CPU 反复读取这些状态位，判断设备状态。

例如伪代码可以写成：

```c
while (设备状态寄存器.busy == 1) {
    // 什么也不做，继续等
}
```

也就是：

```c
while (设备还忙) {
    一直查;
}
```

**第 1 步：从状态寄存器读取忙位，直到该位清零**

CPU 先查看设备状态寄存器里的 **Busy 位**。

如果 Busy = 1，说明设备正在忙，CPU 继续等待。

如果 Busy = 0，说明设备空闲，可以接受新的 I/O 命令。

所以这一步相当于：

```c
while (Busy == 1) {
    继续检查;
}
```

**第 2 步：主机设置读或写位**

CPU 告诉设备：这次操作是读还是写。

例如：

- 读操作：从设备读取数据到 CPU/内存
- 写操作：把 CPU/内存中的数据写到设备

如果是写操作，CPU 还要提前把数据放到 **数据输出寄存器** 中。

例如向打印机输出一个字符时，CPU 要先把字符放进数据寄存器。

**第 3 步：主机设置命令就绪位**

CPU 设置 **Command Ready 位**，表示：

我已经把命令、数据、读写方向都准备好了，设备可以开始工作了。

这个位相当于 CPU 对设备说：“开始执行吧。”

**第 4 步：控制器设置忙位**

设备控制器看到命令就绪位后，会把 Busy 置为 1。

意思是：

我开始处理这个 I/O 请求了，现在不要再给我新命令。

**第 5 步：控制器读取命令寄存器并执行 I/O 操作**

设备控制器读取 CPU 设置好的命令，比如：

- 要读还是写
- 要处理哪个端口
- 数据在哪里

然后它执行具体 I/O 操作。

如果是读操作，设备会把数据放到 **数据输入寄存器** 中。  
如果是写操作，设备会从 **数据输出寄存器** 取出数据并发送到设备。

**第 6 步：传输完成后，控制器清除相关状态位**

操作完成后，控制器会：

- 清除 Busy 位，表示设备不忙了
- 清除 Error 位，或者设置 Error 位表示出错
- 清除 Command Ready 位，表示这次命令处理完了

这时 CPU 下一次轮询时就会发现 Busy = 0，可以继续进行下一次 I/O。

**为什么轮询会浪费 CPU？**

因为 CPU 在等待设备期间没有做有用的计算，而是在不断检查 Busy 位。

例如：

```c
while (Busy == 1) {
    // CPU 一直空转
}
```

CPU 时间都浪费在“问设备好了没有”上。

所以图中说：

如果设备运行缓慢，则效率低下，CPU资源浪费。

这就是轮询的主要缺点。

# 中断IO

中断方式下，CPU 不需要一直等设备。

流程大致是：

1. CPU 向 I/O 设备发出读/写命令；
2. 设备自己慢慢执行；
3. CPU 去执行其他程序；
4. 设备完成后，向 CPU 发出 **中断请求**；
5. CPU 暂停当前程序，转去执行对应的 **中断服务程序**；
6. 处理完 I/O 后，再回到原来的程序继续执行。

可以理解成：

CPU 不再一直问“好了没”，而是告诉设备：“你做完了叫我。”

|**对比项**|**轮询 I/O**|**中断 I/O**|
|---|---|---|
|谁主动|CPU 主动检查设备|设备主动通知 CPU|
|CPU 是否等待|经常忙等|可以去做其他任务|
|效率|设备慢时效率低|一般更高|
|实现复杂度|简单|较复杂|
|适合场景|设备很快、等待时间短|设备较慢、完成时间不确定|
|是否需要中断机制|不需要|需要|

# 应用程序IO接口

> 操作系统向应用程序提供的一套统一的 I/O 使用方式，让应用程序不需要直接关心底层设备的具体差异。

比如应用程序想读文件、写文件、接收键盘输入、向屏幕输出、通过网卡收发数据，它并不会直接控制磁盘、键盘、显示器、网卡的硬件寄存器，而是调用操作系统提供的接口，例如：

```
read(fd, buf, size);
write(fd, buf, size);
open("a.txt", O_RDONLY);
close(fd);
```

层次关系：

```
应用程序
   ↓
应用程序 I/O 接口，例如 read/write/open/close
   ↓
操作系统内核 I/O 子系统
   ↓
设备驱动程序
   ↓
具体硬件设备
```

## **为什么说 I/O 系统调用把设备行为封装在泛型类中？**

这里的“泛型类”不用按编程语言里的模板类严格理解，可以理解为 **操作系统把很多设备抽象成几类通用对象**。

比如 Unix/Linux 中常见思想是：

一切皆文件。

无论是普通文件、终端、管道、设备文件、网络 socket，都可以用类似方式操作：

```c
open()
read()
write()
close()
```

例如：

```c
read(键盘, buf, size);
read(文件, buf, size);
read(网络连接, buf, size);
```

从应用程序角度看，都是“读数据”。  
但底层实现完全不同：

|**应用层操作**|**实际设备**|
|---|---|
|从文件 read|磁盘 I/O|
|从键盘 read|键盘输入|
|从 socket read|网卡接收|
|向终端 write|显示器/终端输出|
|向打印机 write|打印设备输出|

应用程序不用关心这些差异。
## **图中列出的设备差异是什么意思？**

这一页后半部分是在说：不同 I/O 设备差异很大，所以操作系统需要提供统一接口。

### **1. 字符流或块**

有些设备按字符流传输：

```text
键盘、鼠标、串口、终端
```

数据一个字符、一个字节地来。

有些设备按块传输：

```text
磁盘、SSD、U盘
```

数据通常一块一块读写，比如 4KB、512B。
### **2. 顺序或随机访问**

有些设备只能顺序访问：

```text
磁带、网络流、键盘输入
```

数据来了就按顺序处理。

有些设备可以随机访问：

```text
磁盘、SSD、内存映射文件
```

可以指定位置读取，例如读取文件第 1000 个字节之后的数据。
### **3. 同步或异步**

同步 I/O：

应用程序发起 I/O 后，要等 I/O 完成才能继续。

比如：

```c
read(fd, buf, size);
```

如果没有数据，程序可能阻塞等待。

异步 I/O：

应用程序发起 I/O 后可以继续做别的事，I/O 完成后再通知它。
### **4. 共享或专用**

共享设备：

```text
磁盘、网卡
```

多个程序可以共同使用。

专用设备：

```text
某些打印机、独占串口设备
```

某一时刻可能只能被一个程序占用。

### **5. 操作速度**

不同设备速度差异很大。

例如：

```text
键盘很慢
磁盘中等
SSD较快
内存最快
网络速度不稳定
```

操作系统需要屏蔽这些速度差异，让应用程序用统一方式访问。

### **6. 读写、只读或只写**

有些设备可读可写：

```text
磁盘、socket
```

有些设备只读：

```text
键盘、传感器
```

有些设备只写：

```text
显示器、打印机
```

但是在应用程序接口层，它们仍然可以被抽象成统一的 I/O 对象。

**应用程序 I/O 接口就是操作系统给应用程序提供的统一 I/O 调用方式。它把各种设备抽象成类似文件、流、socket 等统一对象，使应用程序可以用 open/read/write/close 等接口操作设备，而不用直接关心底层硬件和驱动的差异。**
