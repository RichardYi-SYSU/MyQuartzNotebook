
## 生产者-消费者问题解决方案

- 在缓冲区队列（循环队列）中使用in和out两个指针，前者指向生产者，后者指向消费者
- 若`in=out`，则队空
- 若`((in + 1) % BUFFER_SIZE) == out`即in再往前走一步就会追上`out`，说明队列已满
- 如果使用`counter`，初始化为0，可以解决最大容量为`Buffer_size-1`的问题，但是多个进程访问`counter`会产生竞争：允许两个进程并发操作变量`counter`，所以得不到正确的状态

## 竞争条件

- 多个进程并发访问和操作同一数据并且执行结果与访问顺序有关
- 为防止竞态条件，需确保一次只有一个进程访问关键数据
- 竞争条件在OS中普遍存在
- 竞争条件是不确定的

## 临界区问题

- 每个进程都有一段代码，称为临界区
	- 进程可能是更改公共变量、更新表、写入文件等
	- 当一个进程处于临界区时，其他进程不得处于其临界区
- 每个进程必须在入口区（entry section）请求进入临界区的许可，临界区之后是退出区（exit section），然后是剩余区（reminder section）

### 解决访问的要求

- **互斥Mutual exclusion** 如果进程Pi在其临界区执行，则其他进程不能在其临界区执行
- **推进Progress** 如果没有进程在其临界区执行，并且存在一些希望进入其临界区的进程，则不能无限期推迟选择下一个将进入临界区的进程
- **有限等待Bounded waiting** 在进程发出进入其临界区的请求后，以及在该请求被批准之前，其他进程允许进入其临界区的次数必须存在上限
	- 假设每个进程以非零速度执行


### 互斥解决方案

- （互斥是手段）
- 软件方法，让并发执行的进程承担，需要与另一个进程合作，而不需要程序设计语言或者操作系统提供任何支持
- 涉及专用机器指令，优点是减小开销，但难以通用
- 在OS或程序设计语言中提供某种级别支持
- **同一时刻最多一个进程进入临界区就是互斥**


### 硬件同步

中断禁用
- 单处理器系统
- 禁用中断保障互斥

缺点
- 代价很高，执行效率会下降
- 不适用于多处理器场景，禁用中断不能保证互斥

**特殊的硬件指令**

- `test_and_set()`测试和设置指令

```c
boolean test_and_set(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;
}
```

```c
do { 
	while (test and set(&lock)); /* do nothing */ 
	/* critical section */ 
	lock = false; 
	/* remainder section */ 
} while (true);
```

**情况A：锁是空的**
```text
test_and_set(&lock)：
    返回 false
    同时把 lock 设为 true
```

于是：

```c
while(false) → 不进入循环
```

当前进程成功进入临界区

**情况 B：锁已被占用（lock = true）**

```text
test_and_set(&lock)：
    返回 true
    lock 仍是 true
```

于是：

```c
while(true) → 一直循环
```

当前进程被卡住（自旋等待）

**离开临界区**

```c
lock = false;
```

表示：

```text
释放锁
```

其他进程下一次 `test_and_set` 就可能成功。

**为什么能实现互斥？**

关键在这句：

```text
test_and_set 是原子的
```

意味着：

```text
同一时刻只有一个进程能看到 lock = false 并成功改成 true
```

其他进程要么：

- 看到的是 true → 进不去
- 要么还没轮到执行

因此保证：

```text
同一时刻最多一个进程进入临界区
```

这就是互斥

- `compare_and_swap()`比较和交换指令
--- 

这里用的是 **compare_and_swap，也叫 CAS**，也是一种硬件原子指令，用来实现互斥锁。

核心函数：

```c
compare_and_swap(&lock, 0, 1)
```

意思是：

```text
如果 lock 当前值等于 0，
就把 lock 改成 1；
然后返回 lock 原来的值。
```

约定：

```text
lock = 0  表示锁空闲
lock = 1  表示锁被占用
```

进入临界区时：

```c
while (compare_and_swap(&lock, 0, 1) != 0)
    ;   // do nothing
```

分两种情况：

**情况 1：锁空闲**

```text
lock 原来是 0
CAS(&lock, 0, 1) 返回 0
同时把 lock 改成 1
```

于是：

```c
while (0 != 0)  // false
```

进程成功进入临界区。

**情况 2：锁已被占用**

```text
lock 原来是 1
CAS(&lock, 0, 1) 返回 1
lock 不变，还是 1
```

于是：

```c
while (1 != 0)  // true
```

进程继续忙等。

离开临界区时：

```c
lock = 0;
```

表示释放锁。

它能实现互斥的关键是：

```text
比较 lock 是否为 0 + 修改为 1
```

这两个动作是**原子的**，中间不会被其他进程插入。

所以不会出现两个进程同时看到 `lock == 0` 的情况。只有一个进程能成功把 `lock` 从 `0` 改成 `1`。

一句话总结：

```text
CAS 通过“如果锁还是空闲，就原子地把它占用”，保证同一时刻只有一个进程能进入临界区。
```
--- 

特殊机器指令的优势：
- 适用于共享主存储器的单个、多个处理器上任意数量的进程
- 简单易验证
- 可用于支持多个关键部分，每个关键部分都可由其自己变量定义

特殊机器指令的劣势：
- 采用忙等待，当进程等待访问临界区，它会继续消耗处理器时间
- 当一个进程离开临界区，且有多个进程在等待时，会出现饥饿
- **可能出现死锁**

### 互斥锁（软件方案）

> 对于软件方案，还需要底层指令支持原子指令等

- 每个互斥锁是表示锁是否可用的布尔变量
- 通过以下方式保护临界区
- 首先获取一个锁`acquire()`
- 然后释放锁`release()`
- 对`acquire()`和`release()`的调用需为原子的，通常通过硬件原子指令实现
- 需要繁忙等待，这锁也被称为自旋锁
- 优点：当进程在等待锁时，没有上下文切换，在使用锁的时间较短时，自旋锁有用
### 严格备选（软件方案）

严格轮换的思想是：

```c
while (turn != i)
    ;   // 等待

/* critical section */

turn = j;
```

其中：

```text
turn = 0  轮到进程 0
turn = 1  轮到进程 1
```

它确实能保证互斥：  
因为同一时刻 `turn` 只能等于一个值，所以只有一个进程能进入临界区。

但它有缺点：**太严格**。

例如：

```text
进程 A 用完临界区，把 turn 交给 B
但 B 根本不想进入临界区
A 想再次进入，却必须等 B
```

这就会造成不必要的等待。

所以关系可以总结为：

```text
严格轮换：
    是早期的软件互斥方案
    不需要硬件原子指令
    能保证互斥
    但效率和灵活性差
```

一句话：  
**严格轮换也是为了实现互斥，但它是软件层面的早期方案；硬件同步是更底层、更可靠的方案，互斥锁通常建立在硬件同步原语之上。**

**不满足Progress条件**


### Peterson解决方案

是两个进程互斥进入临界区的经典软件算法，满足这三个条件[[第七章：同步#解决访问的要求]]

逻辑为：
```
我想进 → 先让对方 → 如果对方也想进并且轮到对方，我就等
```

使用两个共享变量`int turn `和`interested[2]`

对进程 `Pi`，另一个进程为 `Pj`：

```c
flag[i] = true;     // 我想进入临界区
turn = j;           // 先让对方
while (flag[j] && turn == j)
    ;               // 忙等

// 临界区

flag[i] = false;    // 退出临界区
```

核心思想是：

当两个进程都想进入临界区时，`turn` 决定谁等待；如果只有一个进程想进入，它可以直接进入。

Peterson 算法满足临界区问题的三个要求：

1. **互斥**：不会有两个进程同时进入临界区。
2. **进步**：如果临界区空闲，想进入的进程可以被选择进入。
3. **有限等待**：一个进程不会无限期等待。

缺点是它只适用于**两个进程**，并且依赖严格的内存读写顺序，在现代多核处理器上通常需要内存屏障支持。

#### 例子1

以两个进程 **P0** 和 **P1** 为例。

共享变量初始为：

```c
turn = 0 或 1 都可以;
interested[0] = FALSE;
interested[1] = FALSE;
```

假设 **P0 和 P1 几乎同时想进入临界区**。

**步骤 1：P0 想进入**

P0 执行：

```c
interested[0] = TRUE;
turn = 1;
```

意思是：

P0 表示“我想进”，但把机会先让给 P1。

此时：

```c
interested[0] = TRUE
interested[1] = FALSE
turn = 1
```

P0 检查：

```c
while (turn == 1 && interested[1] == TRUE)
```

因为 `interested[1] == FALSE`，所以 P0 不等，进入临界区。

**步骤 2：P1 也想进入**

P1 执行：

```c
interested[1] = TRUE;
turn = 0;
```

意思是：

P1 表示“我也想进”，但把机会先让给 P0。

此时：

```c
interested[0] = TRUE
interested[1] = TRUE
turn = 0
```

P1 检查：

```c
while (turn == 0 && interested[0] == TRUE)
```

两个条件都成立，所以 P1 忙等待。

**步骤 3：P0 在临界区中执行**

现在：

```text
P0：在临界区
P1：忙等待
```

这就保证了**互斥**：不会两个进程同时进入临界区。

**步骤 4：P0 离开临界区**

P0 执行：

```c
interested[0] = FALSE;
```

表示：

P0 不想进入临界区了。

此时 P1 再检查：

```c
while (turn == 0 && interested[0] == TRUE)
```

现在 `interested[0] == FALSE`，条件不成立。

所以 P1 进入临界区。

**如果两个进程同时想进，最后一次写入 `turn` 的进程会让对方先进入。**

#### 例子2

![[../assets/截屏2026-04-29 15.08.44.png]]

这里接下来运行时不会死锁，因为两个进程虽然都可能执行到：

```c

interested[1] = TRUE;
```

但它们**不可能同时都在 while 里等下去**。

关键在 `turn` 只有一个值。

假设流程是：

**1. P0 执行 4–7 行**

```c
interested[0] = TRUE;
```

此时 P0 想进。

**2. 切换到 P1，P1 执行 4–7 行**

```c
interested[1] = TRUE;
```

此时 P0、P1 都想进。

**3. P0 执行 8–9 行**

对 P0 来说：

```c
other = 1;
turn = 1;
while (turn == 1 && interested[1] == TRUE)
```

此时条件成立，所以 **P0 会等待 P1**。

但是接下来如果切换到 P1，P1 会执行第 8 行：

```c
turn = 0;
```

对 P1 来说：

```c
other = 0;
while (turn == 0 && interested[0] == TRUE)
```

这时条件成立，P1 等 P0。

乍一看好像都在等。

但注意：**P1 写** **`turn = 0`** **会改变 P0 的等待条件**。

接下来再切到P0时：

```c
turn == 1 && interested[1] == TRUE
```

现在 `turn = 0`，所以 P0 的条件变成：

```c
FALSE && TRUE
```

因此 **P0 不再等待，可以进入临界区**。

所以最终状态是：

```text
P0：进入临界区
P1：忙等待
```

不会出现：

```text
P0 等 P1
P1 等 P0
```

因为 `turn` 不可能同时等于 0 又等于 1。

一句话总结：

**两个进程都想进入时，最后一次写** **`turn`** **的进程会把优先权让给对方，所以至少有一个进程一定能进入临界区，不会死锁。**

### 信号量

- 互斥锁是一种外部强加的控制方案，或者说是全局控制
- 信号量是一种内部主动的控制方案，或者说是局部控制
- 一个受保护的整数变量S，用来控制多个进程/线程对资源的访问
- 通过两个原子操作访问

```c
wait(S)     // 也叫 P(S)
signal(S)   // 也叫 V(S)
```
#### wait做什么

```c
wait(S) {
    while (S <= 0)
        ;   // busy wait
    S--;
}
```

含义是：

如果 `S > 0`，说明资源可用，就把 `S` 减 1，然后进入。

如果 `S <= 0`，说明资源不可用，就一直等待。

例如：

```c
S = 1
P0 执行 wait(S)：S 变成 0，P0 进入临界区
P1 执行 wait(S)：发现 S <= 0，只能等待
```
#### signal做什么

```c
signal(S) {
    S++;
}
```

含义是：

进程使用完资源后，执行 `signal(S)`，把资源数量加 1，表示释放资源。

例如：

```c
P0 离开临界区，执行 signal(S)
S 从 0 变成 1
P1 现在可以继续执行 wait(S)，进入临界区
```

#### 作用

它可以用来实现：

```c
wait(S);

// 临界区

signal(S);
```

如果 `S` 初值为 1，就是**互斥信号量**，效果类似一把锁：

```text
S = 1：没人占用，可以进入
S = 0：有人占用，必须等待
```

所以：

```c
Semaphore mutex = 1;

wait(mutex);
// critical section
signal(mutex);
```

可以保证同一时刻只有一个进程进入临界区。

同时，信号量不是系统自动帮你管，而是程序员要在合适的位置写：

```c
wait(S);
signal(S);
```

**wait 是申请资源，资源数减 1；signal 是释放资源，资源数加 1。**

考试里常写成：

```text
P 操作：wait，申请资源
V 操作：signal，释放资源
```

#### 三个重要结论

**1. 执行`wait(S)`前，不知道会不会阻塞**

因为 `S` 的值可能刚好被其他进程改变。

```text
你看到 S > 0，不代表下一刻执行 wait 时仍然 > 0
```

所以必须把 `wait(S)` 当成原子操作。

**2. 单处理器上，也不知道哪个进程会马上继续运行**

即使只有一个 CPU，两个进程并发执行时，操作系统可能在任意时刻发生调度切换。

所以不能假设：

```text
我 signal 之后，一定是某个特定进程马上运行
```

**3. 执行`signal(S)`后，不知道是否真的唤醒了进程

因为可能：

```text
没有进程在等 → 唤醒 0 个
有进程在等 → 唤醒 1 个
```

所以 `signal(S)` 的效果可能只是让 `S++`，也可能唤醒一个等待进程。

**信号量只保证同步规则，不保证你能预测进程调度顺序。**

#### 强弱信号量

**强信号量**和**弱信号量**的区别主要在于：  
当多个进程等待同一个信号量时，`signal()` 唤醒谁是否有规则。

**弱信号量不保证等待进程的唤醒顺序。**

```text
signal(S) 后，可能唤醒任意一个等待进程
```

问题是：某个进程可能一直抢不到机会，导致**饥饿**。

**强信号量保证等待进程按某种公平顺序被唤醒，常见是 FIFO 队列。**

```text
先等待的进程先被唤醒
```

因此可以避免长期等待，满足更强的公平性。

能否完全解决忙等待问题？

### 管程

- 是一种比信号量更高级的进程/线程同步机制
- 将三样东西封装到一起：“共享数据+操作共享数据的过程/函数+同步控制”
- 管程属于抽象数据类型，封装了数据及对其操作的一组函数，内部变量只能由过程中的代码访问
- 提供一组由程序员定义的在管程内互斥的操作
- 自动互斥的共享资源管理模块，用条件变量实现等待和唤醒

#### 管程的特点

**1. 数据只能由管程内部过程访问**：

- 管程里有自己的局部共享数据，外部进程不能直接改变它
- 只能通过管程提供的函数访问，能够避免外部修改共享变量

**2. 进程通过调用管程过程进入管程**：

- 进程不是直接操作共享数据，而是调用管程的方法。

**3. 同一时刻只有一个进程能在管程内执行**：

- 如果P0已经在管程里执行，P1再调用管程过程，就必须等待
- 自动保证互斥，不用程序员手动写

#### 用信号量实现管程

- 定义Mutex为1代表管程空闲，可以有一个进程进入
- Mutex为0代表管程已被占用，其他进程不能进入
- Mutex可被视作一把钥匙：mutex = 1：钥匙在门口，能进mutex = 0：钥匙被别人拿走了，不能进

**使用信号量实现管程**

```c
semaphore mutex = 1;
semaphore next = 0;
int next_count = 0;
```

其中：

- `mutex`：保证同一时刻只有一个进程进入管程
- `next`：用于处理被 `signal` 唤醒后需要立刻进入管程的进程
- `next_count`：记录有多少进程在 `next` 上等待

每个管程过程都改成：

```c
wait(mutex);

// 管程过程主体

if (next_count > 0)
    signal(next);
else
    signal(mutex);
```

意思是：

进入管程前先拿锁，退出时如果有被唤醒的进程等着，就优先把管程交给它；否则释放普通互斥锁。

## 经典同步问题

### 有界缓冲区同步（生产者-消费者）问题

> 对此问题的描述：一个或多个生产者产生数据并将其放入缓冲区，单个消费者一次从缓冲区取出一个项目，任何时候只有一个生产者或消费者可以访问缓冲区

场景是：

```text
有 n 个缓冲区
生产者往缓冲区放产品
消费者从缓冲区取产品
```

要解决两个问题：

1. **不能同时操作缓冲区**
2. **满了不能再放，空了不能再取**

这里用了 3 个信号量：

- **`mutex = 1`**

互斥锁，保护缓冲区。

```text
mutex = 1：缓冲区没人操作
mutex = 0：缓冲区正在被操作
```

- **`empty = n`**

表示空缓冲区数量。

```text
empty = n：一开始有 n 个空位
empty = 0：缓冲区满了，生产者不能再放
```

生产者放东西前要：

```c
wait(empty);
```

意思是：先申请一个空位。

- **`full = 0`**

表示满缓冲区数量，也就是已有产品数量。

```text
full = 0：一开始没有产品
full = n：缓冲区全满
```

消费者取东西前要：

```c
wait(full);
```

意思是：先申请一个产品。

**生产者流程**

```c
produce item;

wait(empty);   // 等一个空位
wait(mutex);   // 进入缓冲区

add item;

signal(mutex); // 离开缓冲区
signal(full);  // 产品数 +1
```

锁类型的信号量，比如这里的mutex，是在同一个进程里获取/释放的，而非锁类型的信号量，比如empty、full，描述的是缓冲区状态

**消费者流程**

```c
wait(full);    // 等一个产品
wait(mutex);   // 进入缓冲区

remove item;

signal(mutex); // 离开缓冲区
signal(empty); // 空位数 +1

consume item;
```

**`empty`** **控制生产者别把缓冲区放满；`full`控制消费者别从空缓冲区取；`mutex`保证同一时刻只有一个进程操作缓冲区。**

### 对于课件104页的问题

错误的点在于`if(n==0)`这条语句的对共享变量n的判断不在互斥保护内，因此当消费者取走最后一个产品后，如果生产者马上运行`append();n++;if (n == 1) semSignalB(delay);`那么消费者继续运行时就不会等待，即不会把delay-1，继续运行循环，导致n变为-1，出错


想通过把`semSignalB(s)`放到`if(n==0)`的下方来解决，其实不行。因为`n==0`时，消费者持有互斥锁s，阻塞在delay上，
不能直接这样改。

这样生产者想生产时需要：

```c
semWaitB(s);
```

但 `s` 被消费者占着，生产者进不来，也就不能执行：

```c
n++;
semSignalB(delay);
```

于是发生死锁。（临界区不能无限大，否则易出现死锁）

**不能拿着互斥锁去等待另一个信号量，否则可能阻塞别人唤醒你。**

### 读者写者问题

- 指多个进程/线程共享同一份数据，比如文件、数据库、缓存
- 同步要求是多个读者可以同时读、写者写的时候，不能有其他读者或写者
- 相较于生产消费者问题，这里更关注共享数据访问权限：读者之间不互斥，写者和任何人互斥

#### 读者优先写法

**对于读者：**

[[操作系统/materials/2026-OS-CH-7-同步.pdf#page=111|2026-OS-CH-7-同步, 页面 111]]此处用两个信号量和一个计数器，

```c
int readcount = 0;//当前正在读的读者数量
semaphore x = 1;//保护 readcount 的互斥锁
semaphore wsem = 1;//控制写权限，写者独占
```

进入读区前：

```c
semWait(x);
readcount++;
if (readcount == 1)
    semWait(wsem);
semSignal(x);
```

- 第一个读者进来时，执行`semWait(wsem)`可以获得写者的锁，这样写者就不能写了，而`if(readcount==1)`则可以确保后来的读者只需要增加readcount，而不用再锁wsem，一起读

读完后：

```c
semWait(x);
readcount--;
if (readcount == 0)
    semSignal(wsem);
semSignal(x);
```

- 最后一个读者离开时，释放wsem，写者才有机会写

**对于写者：**

```c
semWait(wsem);
WRITEUNIT();
semSignal(wsem);
```

- 写者必须先拿到wsem，如果有读者正在读，wsem就被第一个读者占着，写者只能等

**第一个读者锁住写者，最后一个读者释放写者；写者写的时候独占 wsem。**

#### 写者优先

**一旦有写者在等待，就阻止新的读者进入；等写者写完后，再允许读者继续。**

```c
readcount   // 当前正在读的读者数
writecount  // 当前正在等待/写入的写者数

x = 1       // 保护 readcount
y = 1       // 保护 writecount
z = 1       // 让读者排队，避免多个读者同时抢 rsem
wsem = 1    // 写资源锁，控制真正读/写
rsem = 1    // 读者入口锁，写者用它阻止新读者进入
```

写者进入时：

```c
semWait(y);
writecount++;
if (writecount == 1)
    semWait(rsem);
semSignal(y);
```

第一个写者到来后，会锁住rsem，后来的读者执行`semWait(rsem)`时会被挡住，不能再进入读区
