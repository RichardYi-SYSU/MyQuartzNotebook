
# 死锁概念

- 当一组进程中的每个进程都在等待某个事件（资源），而仅有这组进程中被阻塞的其他进程才可出发该事件时，则认为该组进程发生了死锁
- 死锁具有永久性
- 其没有有效而通用的解决方案

# 资源定义

- 资源包括硬件资源和软件资源
- 不论资源类型，都会产生死锁

## 可重用资源

- 一次只能安全地被一个进程使用，但使用完之后资源本身不会消失
- 比如：CPU、IO通道、主存辅存、设备、文件、数据库、信号量
- 使用流程为：申请->使用->释放

## 可消耗资源

- 可以被产生，也可以被消耗，一旦被使用，就可能不存在了
- 比如中断、信号、消息、IO缓冲区中的数据

# 死锁必要条件

## 互斥

- 一次只有一个进程使用一个资源，其他进程不能访问分配给其他进程的资源

## 占用等待

- 当一个进程等待其他进程时，继续占用已分配的资源

## 非抢占

- 不能强行抢占已占有的资源

## 循环等待

- 存在一个闭合的进程链，每个进程至少占有此链中下一个进程所需的一个资源

## 资源分配图

- 请求边：由进程指向资源
- 分配边：由资源指向进程，资源可有多个出口
- 如果资源分配图中没有环，那么系统就没有进程死锁，如果有环，可能存在死锁

# 死锁预防策略

## 处理死锁的方法

- 确保系统永远不会进入死锁状态
	- 死锁预防
	- 死锁避免
- 允许系统进入死锁状态，然后检测和恢复
- 忽略该问题，假装系统中从未发生死锁：大多采用的方法

## 预防策略

使死锁四个必要条件之一无效：

### 破坏互斥

可共享资源（只读文件）不需要互斥，通常不能否定互斥条件来预防死锁，需保留不可共享的资源

### 破坏占有等待（持有且等待）

必须保证每当进程请求资源时，它不会保持任何其他资源

- 在开始执行之前请求并分配所有资源
- 仅当进程在未分配任何资源时才允许进程请求资源
- 资源利用率低，资源已经分配，但长时间不用，发生饥饿

### 破坏非抢占

- 如果持有某些资源的进程请求另一个无法立即分配给它的资源，那么当前持有的所有资源都将被释放（隐式释放）
- 被抢占资源被添加到进程正在等待的资源列表中
- 只有当进程能够恢复其原有的资源以及它所请求的新资源时，才会重启进程

#### 例子

比如有一个进程 **P1** 正在运行，它已经拿到了：

- 资源 A：打印机
- 资源 B：文件锁

这时 P1 又请求一个新资源：

- 资源 C：扫描仪

但是扫描仪现在被别的进程占用，**不能立刻分配给 P1**。

在“无抢占”策略下，系统会这样做：

1. **P1 已经占有的打印机和文件锁会被隐式释放**
2. **P1 请求不到的扫描仪会被加入等待列表**
3. P1 暂停，等以后条件满足
4. 只有当 P1 能重新获得：
    
    - 原来的打印机
    - 原来的文件锁
    - 新请求的扫描仪
    
    它才会重新开始运行
    

可以理解成：

P1 本来手里拿着打印机和文件锁，又想要扫描仪。  
但扫描仪没空。于是系统让 P1 先把手里的资源都放下，去排队。  
等打印机、文件锁、扫描仪都能一起给它时，再让它继续执行。

### 破坏循环等待

- 强制所有类型资源进行完全排序，并要求每个进程以增强的顺序请求资源
- 最常见，只需为每个资源分配一个编号，从小到大申请资源

#### 例子

比如规定资源编号：

|**资源**|**编号**|
|---|---|
|打印机|1|
|扫描仪|2|
|数据库锁|3|

规则是：**进程只能按编号递增的顺序申请资源**。

例如：

P1 可以这样申请：

先申请打印机 1 → 再申请扫描仪 2 → 再申请数据库锁 3

这是合法的，因为编号越来越大。

但 P2 不能这样申请：

先申请数据库锁 3 → 再申请打印机 1

这是不合法的，因为它从编号大的资源倒回去申请编号小的资源。

为什么这样可以避免死锁？

假设有两个进程：

- P1 已经拿着打印机 1，正在等扫描仪 2
- P2 已经拿着扫描仪 2，想等打印机 1

如果允许这样，就会死锁：

P1 等 P2 的扫描仪，P2 等 P1 的打印机。

但是按照“必须从小到大申请资源”的规则，P2 拿着扫描仪 2 后，就**不能再去申请打印机 1**。

所以这个循环就形成不了。

简单理解：

所有人拿资源都只能“往编号大的方向拿”，不能回头拿编号小的资源。  
既然不能回头，就不可能绕成一个圈。  
没有圈，就没有循环等待，也就避免了死锁。


# 死锁避免

## 与死锁预防的区别

|**对比点**|**死锁预防**|**死锁避免**|
|---|---|---|
|思想|破坏死锁必要条件|避免进入不安全状态|
|时机|事先制定严格规则|每次资源申请时动态判断|
|是否需要最大需求信息|通常不需要|需要|
|资源利用率|较低|较高|
|系统吞吐率|较低|较高|
|典型方法|资源编号、一次性申请、资源可抢占|银行家算法|
|缺点|太保守，限制多|计算复杂，需要先验信息|

## 安全状态

- 当进程请求可用资源时，系统必须决定立即分配是否使系统处于安全状态
- 只有存在一个安全序列，系统才处于安全状态
- 安全状态不是死锁状态
- 死锁状态是非安全状态
- 不是所有的非安全状态都能导致死锁状态
- 非安全状态可能导致死锁

### 例子

对于[[操作系统/materials/2026-OS-CH-8-死锁.pdf#page=21|2024-OS-CH-8-死锁, 页面 21]]

系统总共有 **12 台磁带驱动器**。

当前分配情况：

|**进程**|**最大需求 Max**|**当前已分配 Allocation**|**还需要 Need = Max - Allocation**|
|---|---|---|---|
|P0|10|5|5|
|P1|4|2|2|
|P2|9|2|7|

当前已经分配出去：

5 + 2 + 2 = 9

所以系统当前可用资源：

12 - 9 = 3

现在判断有没有**安全序列**。

---

当前可用资源是 **3 台**。

先看谁还能被满足：

- P0 还需要 5 台，3 不够；
- P1 还需要 2 台，3 够；
- P2 还需要 7 台，3 不够。

所以可以先让 **P1** 执行完。

P1 执行完成后，会释放它已经占有的 2 台磁带机。拿两台，剩一台，运行完后释放四台，因此3-2+4=5台

此时可用资源变成：

3 + 2 = 5

现在看：

- P0 还需要 5 台，够；
- P2 还需要 7 台，不够。

所以可以让 **P0** 执行完。

P0 执行完成后，释放它占有的 5 台。

此时可用资源变成：

5 + 5 = 10

现在 P2 还需要 7 台，10 台够用，所以 **P2** 也可以执行完成。

因此存在一个安全序列：

$P1 \rightarrow P0 \rightarrow P2$

所以当前状态是：**安全状态**。

核心判断方法就是：

看当前可用资源能不能先满足某个进程；  
这个进程完成后释放资源；  
再继续看能不能满足下一个进程；  
如果最后所有进程都能完成，就是安全状态。

## 死锁避免的两种方法

### 资源分配拒绝

意思是：
进程已经开始运行了。  
当它后来继续申请资源时，系统要先判断：如果现在把资源分配给它，会不会让系统进入不安全状态。  
如果可能导致死锁，就暂时拒绝这次资源申请。

也就是：**不是有资源就马上给，而是给之前先做安全性检查。**

**例子：**

系统有 12 台磁带机，当前某个进程 P0 又申请 1 台。

系统会先假设：

如果给 P0 这 1 台，系统还能不能找到一个安全序列？

如果还能找到安全序列，就分配；  
如果找不到，就不分配，让 P0 等待。

这个方法对应常见的 **银行家算法**。

### 进程启动拒绝

意思是：
在一个新进程开始运行之前，系统先看它声明的最大资源需求。  
如果让它加入系统后，可能导致系统进入不安全状态，就干脆先不启动这个进程。

也就是：**从源头控制，不让危险进程开始执行。**

**例子：**

系统一共有 12 台磁带机。

现在已经有几个进程在运行，它们加起来可能最多需要 10 台。

这时来了一个新进程 P3，它声明最多需要 5 台。

如果启动 P3，那么系统总的最大可能需求变成：10 + 5 = 15 台

超过系统总量 12 台，可能导致死锁风险。

所以系统可以暂时不启动 P3，等其他进程完成并释放资源后再启动它。

## 资源分配图算法

这里讲的是**资源分配图算法 Resource-Allocation Graph Algorithm**，它是一种**死锁避免**方法，适用于：

**每种资源类型只有一个实例**的情况。  
比如只有一台打印机、一个扫描仪、一个文件锁。

它的核心思想是：

进程申请资源时，系统先假设把资源分配给它，看看资源分配图里会不会形成环。  
如果形成环，就说明可能进入不安全状态，不分配；  
如果不形成环，就可以分配。

**1. 图中有哪些点和边？**

资源分配图里有两类节点：

|**节点**|**含义**|
|---|---|
|圆形节点|进程 / 线程，比如 T1、T2|
|方形节点|资源，比如 R1、R2|

边有三种：

|**边**|**形式**|**含义**|
|---|---|---|
|请求边|Pi → Rj|进程 Pi 正在请求资源 Rj|
|分配边|Rj → Pi|资源 Rj 已经分配给进程 Pi|
|需求边 / 声明边|Pi ⇢ Rj，虚线|进程 Pi 以后可能会请求资源 Rj|

---

**2. 什么叫“需求边”？**

需求边是这页的重点。

虚线：

Pi ⇢ Rj

表示：

进程 Pi 未来可能会申请资源 Rj。

它不是现在正在申请，而是**提前声明**。

例如：

- T1 未来可能需要 R1 和 R2；
- T2 未来也可能需要 R1 和 R2。

系统一开始就要知道这些可能需求，所以幻灯片写了：

必须在系统中预先声明资源。

也就是：进程开始前，要先告诉系统“我以后可能会用哪些资源”。

---
**3. 边是怎么变化的？**

资源分配图算法里，边会随着进程申请和释放资源而变化。

**情况一：进程还没申请资源**

只有需求边：

Pi ⇢ Rj

意思是：Pi 将来可能申请 Rj。

**情况二：进程真的申请资源**

需求边变成请求边：

Pi → Rj

意思是：Pi 现在正在请求 Rj。

**情况三：系统批准分配**

请求边变成分配边：

Rj → Pi

意思是：Rj 已经分配给 Pi。

**情况四：进程释放资源**

分配边又变回需求边：

Pi ⇢ Rj

意思是：Pi 释放了 Rj，但以后可能还会再申请。

---

**4. 什么时候可以批准资源请求？**

假设进程 Pi 请求资源 Rj。

系统不会马上给，而是先做一次检查：

如果把 Pi → Rj 这条请求边改成 Rj → Pi 这条分配边，图中会不会出现环？

如果**不会出现环**，说明安全，可以分配。

如果**会出现环**，说明不安全，不能分配。

注意这里是死锁避免，不是已经死锁了，而是：

如果现在分配，可能导致以后发生死锁，所以提前拒绝。

---

**5. 看图中的例子**

左边图是一个资源分配图：

- R1 已经分配给 T1，所以有边：R1 → T1；
- R2 还没有真正分配；
- T1 和 T2 对 R2 有虚线需求边，表示未来可能需要 R2；
- T2 也持有或请求某些资源关系。

右边图显示的是一种**非安全状态**。

为什么？

因为如果系统把 R2 分配给 T2，就会形成这种关系：

R1 → T1  
T1 ⇢ R2  
R2 → T2  
T2 → R1

这就形成一个环：

T1 → R2 → T2 → R1 → T1

一旦形成环，就说明有可能出现：

- T1 等 R2；
- R2 被 T2 占着；
- T2 等 R1；
- R1 被 T1 占着。

这样 T1 和 T2 就互相等待，可能死锁。

所以系统会判断：

如果把 R2 分配给 T2，会产生环。  
因此这次分配不能批准。

---
**6. 为什么“有环”就是危险？**

因为这里有一个前提：

每种资源类型只有一个实例。

也就是说：

- R1 只有一个；
- R2 只有一个。

在这种情况下，如果图里形成环，就说明资源之间出现了互相等待关系。

例如：

T1 等 T2 手里的资源，T2 又等 T1 手里的资源。

这就非常危险。

所以资源分配图算法用“环检测”来判断是否安全。

---
**7. 和银行家算法的区别**

这两个都是死锁避免方法，但适用场景不同：

|**方法**|**适用情况**|**判断方式**|
|---|---|---|
|资源分配图算法|每种资源只有一个实例|看图中是否形成环|
|银行家算法|每种资源可以有多个实例|检查是否存在安全序列|

所以这页最后写：

每种资源类型只有一个实例。

这是资源分配图算法的重要限制。

---

一句话总结：

**资源分配图算法就是：进程先声明未来可能要的资源；每次真正申请资源时，系统先假设分配，看图中会不会成环；如果成环就拒绝，不成环才分配。**


## 银行家算法

- 包含两部分，分别为安全性算法和资源请求算法
- 银行家算法每次分配资源前，都会先进行一次“试探性分配”，然后检查系统是否还能找到一个安全序列；能找到就分配，找不到就拒绝。

### 前置相关数据结构

设：

- `n`：进程数
- `m`：资源类型数

**Available**

`Available[j]` 表示当前系统中 **第 j 类资源还剩多少个可用实例**。

例如：

```text
Available = [3, 2, 1]
```

表示资源 `R0` 还剩 3 个，`R1` 还剩 2 个，`R2` 还剩 1 个。

**Max**

`Max[i][j]` 表示进程 `Pi` 对资源 `Rj` 的 **最大需求量**。

例如：

```text
Max[1][2] = 4
```

表示进程 `P1` 最多可能需要 4 个 `R2`。

**Allocation**

`Allocation[i][j]` 表示进程 `Pi` 当前已经分配到的资源 `Rj` 数量。

例如：

```text
Allocation[1][2] = 2
```

表示 `P1` 当前已经拿到了 2 个 `R2`。

**Need**

`Need[i][j]` 表示进程 `Pi` 还需要多少个资源 `Rj` 才能完成任务。

公式是：

```text
Need[i][j] = Max[i][j] - Allocation[i][j]
```

比如：

```text
Max[1][2] = 4
Allocation[1][2] = 2
```

那么：

```text
Need[1][2] = 2
```

表示 `P1` 还需要 2 个 `R2` 才可能完成。

### 安全性算法

- 用于判断当前系统是否处于安全状态（即存在一个进程序列，使得所有进程都能依次完成，这一序列叫做安全序列）

1. **初始化 Work 和 Finish**

定义：

```text
Work = Available
```

`Work` 表示当前可用于分配的资源数量。

然后初始化：

```text
Finish[i] = false
```

表示每个进程一开始都还没有完成。

例如有 5 个进程：

```text
Finish = [false, false, false, false, false]
```

2. **寻找一个可以完成的进程**

找一个进程 `Pi`，满足两个条件：

```text
Finish[i] == false
Need[i] <= Work
```

这里的 `Need[i] <= Work` 是逐个资源类型比较。

例如：

```text
Need[i] = [1, 0, 2]
Work    = [3, 1, 2]
```

因为：

```text
1 <= 3
0 <= 1
2 <= 2
```

所以这个进程可以运行完成。

含义是：当前系统剩余资源足够满足 `Pi` 的剩余需求，因此可以假设 `Pi` 顺利执行完毕。

3. **假设该进程完成并释放资源**

如果找到这样的进程 `Pi`，那么认为它可以完成，并释放它当前占有的资源：

```text
Work = Work + Allocation[i]
Finish[i] = true
```

例如：

```text
Work = [3, 1, 2]
Allocation[i] = [2, 0, 1]
```

执行完成后：

```text
Work = [5, 1, 3]
```

然后回到 Step 2，继续寻找下一个可以完成的进程。

4. **判断是否安全**

如果最后：

```text
Finish[i] == true
```

对所有进程都成立，那么系统是安全的。

也就是说，存在一个顺序可以让所有进程完成。

如果有某些进程的 `Finish[i]` 仍然是 `false`，说明系统不安全。


### 资源请求算法


当进程 `Pi` 请求资源时，设请求向量为：

```text
Request[i]
```

例如：

```text
Request[i] = [1, 0, 2]
```

表示进程 `Pi` 请求 1 个 `R0`，0 个 `R1`，2 个 `R2`。

1. **检查请求是否超过 Need**

先判断：

```text
Request[i] <= Need[i]
```

如果不满足，说明该进程请求的资源超过了它声明的最大需求，这是非法请求。

2. **检查系统当前是否有足够资源**

判断：

```text
Request[i] <= Available
```

如果不满足，说明当前资源不够，进程必须等待。

3. **试探性分配**

如果前两个条件都满足，系统先“假装”分配资源：

```text
Available = Available - Request[i]
Allocation[i] = Allocation[i] + Request[i]
Need[i] = Need[i] - Request[i]
```

4. **运行安全性算法**

对试探性分配后的状态运行安全性算法。

如果系统仍然安全，就正式分配。

如果系统变成不安全状态，就撤销刚才的试探性分配：

```text
Available = Available + Request[i]
Allocation[i] = Allocation[i] - Request[i]
Need[i] = Need[i] + Request[i]
```

然后让进程等待。

# 死锁检测

## 等待图

- 适用于每个资源类型有单个实例
- 维护一个等待图，节点是进程，Pi->Pj如果Pi正在等待Pj
- 定期调用在图中检测环的算法，如果存在环，则存在死锁
- 由资源分配图->对应等待图只需要略去资源仅保留进程即可，然后看有没有环

## 类银行家算法

- 适用于每个资源类型有多个实例

**1. 初始化**

课件第一步：

```text
Work = Available
```

表示先把当前系统还能用的资源数量复制给 `Work`。

然后：

```text
if Allocation_i ≠ 0:
    Finish[i] = false
else:
    Finish[i] = true
```

这里 `Allocation_i` 指的是进程 `Pi` 当前占有的资源向量。

例如：

```text
Allocation_i = [0, 0, 0]
```

说明 `Pi` 没有占有任何资源，它不可能参与死锁，所以直接设：

```text
Finish[i] = true
```

如果：

```text
Allocation_i = [1, 0, 2]
```

说明 `Pi` 占有资源，有可能参与死锁，所以先设：

```text
Finish[i] = false
```

**2. 找一个“当前请求可以被满足”的进程**

课件第二步：

```text
Find an index i such that:
Finish[i] == false
Request_i <= Work
```

意思是找一个还没判断完成的进程 `Pi`，并且它当前请求的资源数量不超过系统现有可用资源。

注意：

```text
Request_i <= Work
```

是**向量逐项比较**。

例如：

```text
Request_i = [1, 0, 2]
Work      = [3, 1, 2]
```

满足，因为：

```text
1 <= 3
0 <= 1
2 <= 2
```

这说明系统现在就能满足 `Pi` 的请求，因此可以认为 `Pi` 能继续执行，最终完成。

**3. 假设它完成，释放资源**

课件第三步：

```text
Work = Work + Allocation_i
Finish[i] = true
go to step 2
```

这一步的含义是：

既然 `Pi` 当前请求能被满足，那么我们就假设它可以继续执行到结束。结束后，它会释放原来占有的资源 `Allocation_i`。

所以把这些资源加回 `Work`：

```text
Work = Work + Allocation_i
```

然后标记它已经可以完成：

```text
Finish[i] = true
```

接着回到第二步，继续找下一个可以完成的进程。

**4. 判断是否死锁**

课件第四步：

```text
If Finish[i] == false for some i,
then the system is in deadlock state.
Moreover, if Finish[i] == false,
then Pi is deadlocked.
```

也就是说，如果算法最后还有某些进程的 `Finish[i]` 仍然是 `false`，说明这些进程无论如何都无法继续完成。

这些进程就是死锁进程。

**5. 和银行家算法安全性检测的关键区别**

这两个算法形式很像，但判断条件不同。

银行家算法安全性检测用的是：

```text
Need_i <= Work
```

而死锁检测算法用的是：

```text
Request_i <= Work
```

原因是：

银行家算法关心的是：

如果以后进程最多还要这么多资源，系统是否仍然安全？

所以它用 `Need`。

死锁检测算法关心的是：

当前这些进程正在等的资源，是否能被满足？

所以它用 `Request`。

**6. 为什么初始化时 Allocation 为 0 的进程直接 Finish = true？**

因为死锁的本质是：

一组进程互相等待对方占有的资源。

如果某个进程什么资源都没占有，即：

```text
Allocation_i = 0
```

那么它不可能成为“别人等待资源的持有者”，所以它不可能在死锁环里。

因此直接设为：

```text
Finish[i] = true
```

**7. 复杂度为什么是 O(m × n²)**

最多需要找到 `n` 个进程完成。

每次找进程时，最坏要扫描 `n` 个进程。

每检查一个进程，都要比较 `m` 类资源：

```text
Request_i <= Work
```

所以总复杂度是：

```text
O(n × n × m) = O(mn²)
```


多实例死锁检测算法就是不断找一个当前请求 `Request_i` 能被 `Work` 满足的进程，让它“假装完成并释放资源”；最后还不能完成的进程，就是死锁进程。

# 死锁恢复

## 策略

- 取消所有死锁进程，最常用方法
- 把每个死锁进程回滚到前面定义的某些检查点，并重启所有进程，要求在系统中构建回滚和重启机制
- 连续取消死锁进程直到不再存在死锁，所取消的进程的顺序应基于某种最小代价原则
- 连续抢占资源直到不再存在死锁，需要用一种基于代价的选择方法，且需要在抢占后重新调用检测算法

## 最小代价的选择原则

- 目前为止消耗的处理器时间最少
- 目前为止产生的输出最少
- 预计剩下的时间最长
- 目前为止分配的资源总量最少
- 优先级最低
