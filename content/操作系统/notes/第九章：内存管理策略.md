
# 为什么需要内存管理

内存是有限资源，但程序运行必须依赖内存。OS要负责把有限的内存安全、高效地分配给多个程序

## 程序运行必须放在内存中

CPU 执行程序时，需要从内存中取指令和数据。也就是说，程序代码、变量、栈、堆等都要占用内存。

如果没有内存管理，程序不知道该放在哪里，CPU 也无法正常取指执行。

## 多个进程需要同时在内存中

现代 OS 通常不是一次只运行一个程序，而是同时运行多个进程，比如浏览器、编辑器、后台服务等。

## 防止进程互相干扰

每个进程都应该只能访问自己的内存空间。

# 用户空间内存

## 地址空间

- 从低地址到高地址分别为：`Code+Constant->Data Segment & BSS-全局和静态变量->Heap->Stack`
- BSS段用来存放未显式初始化的全局变量和静态变量，以及显式初始化为0的全局变量和静态变量

# 内存管理

- 主存储器和寄存器是CPU可直接访问的唯一存储器
- cache位于主内存和CPU寄存器之间

## 内存保护

- 需要限制进程只能访问其地址空间中的那些地址
- 可以通过使用一对基址寄存器和界限地址寄存器定义进程的可访问地址
- 地址空间提供这种保护，通过CPU硬件实现

## 硬件地址保护

- 就是检查其地址是否满足$base\leq address \le base+limit$
- 确保其内存访问量在基地址和界限之间

## 地址绑定

就是指**把程序中的“逻辑位置”绑定到内存中的“实际位置”**

1. 源代码阶段是符号地址，比如int x中的x
2. 编译阶段是可重定位地址，也就是一种相对形式表示地址
3. 链接/加载阶段，也就是地址绑定后的最终绝对/物理地址

## 逻辑地址空间和物理地址空间

- 逻辑地址由CPU生成，也称为虚拟地址
- 物理地址是内存单元看到的地址
- 逻辑地址空间是程序生成的所有逻辑地址的集合
- 物理地址空间是程序生成的所有物理地址的集合

## MMU（内存管理单元）

将虚拟地址映射到物理地址的硬件设备

- 基址寄存器方案的推广，例如如果基地址为14000，对地址346的访问映射位置为14346
- 用户程序处理逻辑地址，其不会看到真正的物理地址

## 动态加载

程序运行时，并不是一开始就把所有代码都装入内存，而是**等某段代码真正要被调用时，才把它从磁盘加载到内存中执行**。

它解决的问题是：有些程序很大，但不是所有功能都会马上用到，甚至很多功能一次运行中根本不会用到。提前全部加载会浪费内存。

| **概念** | **重点**                |
| ------ | --------------------- |
| 动态加载   | **什么时候把代码加载进内存**      |
| 动态链接   | **什么时候把程序和库函数地址绑定起来** |
**动态加载关注“代码是否已经进内存”；动态链接关注“程序调用的库函数地址是否已经接好”。**

## 动态链接和共享库

- 静态链接：加载程序将系统库和程序代码组合到二进制程序映像中
- 动态链接：程序在生成可执行文件时，**不把库代码完整复制进程序里**，而是等到程序运行时，再由操作系统/动态链接器把需要的库加载进内存，并把程序里对库函数的调用“接上”。

动态链接的优点是：
程序体积小；多个程序可以共享同一份系统库；库更新时，很多程序不需要重新编译就能受益。

缺点是：
运行时依赖库是否存在、版本是否兼容；如果库版本不对，可能出现“找不到动态库”或“符号未定义”等问题。

## 交换

- 正常情况下禁止交换，当空闲内存低于某个阈值时启用交换
- 移动系统通常禁止交换，如果没有足够内存则会终止进程

## 连续分配

主存分为两个分区：

- 常驻操作系统，通常中断向量保存在低地址内存中，操作系统也保存在低地址内存中
- 用户进程保存在高地址内存中
- 每个进程包含在内存的单个连续部分中

```
低地址内存
┌──────────────────┐
│ 中断向量表       │
├──────────────────┤
│ 操作系统内核     │
├──────────────────┤
│ 用户进程         │
│ 用户进程         │
│ 用户进程         │
└──────────────────┘
高地址内存
```

**中断向量放在低地址内存，是因为 CPU 需要在发生中断时快速、固定地找到中断处理程序入口；同时中断向量属于内核管理的数据，放在低地址内核区域便于保护和统一管理。**

## 固定分区

把内存提前切成若干个边界固定、大小固定的区域，每个区域称为一个分区，用户进程只能被装入某个分区中运行

等长固定分区或不等长固定分区

**缺点**

多道程序数量受分区数限制。假如用户区只有 7 个分区，那么最多同时放 7 个用户进程。

容易产生**内部碎片**。例如 3M 的进程放入 8M 分区，浪费 5M。

## 可变分区

当一个进程到达时，从一个足以容纳它的孔中分配内存

进程退出时释放其分区，相邻的空闲分区合并

需要不断记录两类表：

- 已分配分区表：哪些区域被哪个进程占用
- 空闲分区表：哪些区域还是空的，起始地址是多少，大小是多少

**优点**

比固定分区灵活，能减少**内部碎片**

**缺点**

由于其会产生很多分散的小空闲区，比如空闲区分散在不同位置，即使加起来是够新来的进程，但是由于没有一个连续的够这一进程放的，还是放不进去。称为外部碎片。采用可变分区会增加**外部碎片**

### 放置算法

- 首次适应：分配足够大的第一个孔
- 最佳匹配：分配足够大的最小孔，需要搜索整个列表，能够产生最小的剩余孔
- 最差适应：分配最大的孔，需要搜索整个列表，能够产生最大的剩余孔

首次适配算法不仅是最简单的，而且通常是最好和最快的

## 分段

| **对比点** | **分区**              | **分段**           |
| ------- | ------------------- | ---------------- |
| 划分依据    | 按内存空间划分             | 按程序逻辑结构划分        |
| 分配对象    | 通常是整个进程             | 进程中的各个段          |
| 地址形式    | 一个线性地址              | 段号 + 段内偏移        |
| 进程是否连续  | 通常要求整个进程连续          | 各段之间不要求连续        |
| 段/区大小   | 固定或动态               | 各段大小不同，有最大长度     |
| 碎片问题    | 固定分区有内部碎片；可变分区有外部碎片 | 消除明显内部碎片，但仍有外部碎片 |
分区管理：
```
┌────────────┐
│ 进程 A     │  ← 整个进程连续
└────────────┘
```

分段管理：

```
物理内存
┌───────────────┐
│ 进程 A 代码段 │
├───────────────┤
│ 进程 B 数据段 │
├───────────────┤
│ 进程 A 栈段   │
├───────────────┤
│ 空闲区        │
├───────────────┤
│ 进程 A 数据段 │
└───────────────┘
```

一个程序占据多个分区，并且这些分区不要求是连续的

分段能消除内部碎片，是因为段的大小按程序实际需要决定，分配时尽量刚好分配给该段；但由于每个段仍需连续存放，所以会产生外部碎片。

而由于每个段本身仍要求连续存放。内存中如果出现很多分散的小空闲块，就可能出现：
```
空闲区：2M + 3M + 4M
总空闲：9M
```
那么如果有某个段需要5M，还是放不进去，因此外部碎片还是存在

## 分页

| **方式** | **怎么切**            | **分配单位** | **是否要求连续** | **碎片特点**    |
| ------ | ------------------ | -------- | ---------- | ----------- |
| 固定分区   | 物理内存预先切固定块         | 整个进程     | 进程整体连续     | 内部碎片明显      |
| 可变分区   | 按进程大小动态切物理内存       | 整个进程     | 进程整体连续     | 外部碎片        |
| 分段     | 按程序逻辑切成代码段、数据段、栈段等 | 段        | 段内连续，段间不连续 | 外部碎片        |
| 分页     | 逻辑内存和物理内存都切成固定小块   | 页/帧      | 页面之间不连续    | 无外部碎片，有内部碎片 |
能避免外部碎片，因为分页不要求给进程找一整块连续内存，也不要求给某个段找一整块连续内存

只要有足够数量的空闲帧就行

比如进程 A：需要 4 个页框

物理内存中空闲帧可能分散在各处：
```
帧1 空闲
帧5 空闲
帧9 空闲
帧12 空闲
```

分页可以直接把进程的 4 个页面分别放进去：
```
页0 → 帧5
页1 → 帧12
页2 → 帧1
页3 → 帧9
```

### 页表

- 保存在主存中，为每一个进程分配
- 逻辑页表的地址是连续的，但对应的物理页表的地址不一定连续

### 有效访问时间

- 在TLB中找到页码的百分比
- 如果在TLB中找不到所需页面，那么需要两次内存访问

### 内存保护

将保护位与每个帧关联以指示是否允许只读或读写访问来实现内存保护

### 页帧与页

- 页帧Frame本质上是块空间，空的框架，在内存中
- 页Page本质上是相关的数据，在磁盘中
- 内存管理指的是将磁盘中页的内容放进内存的页帧中

### 分层页表

[[操作系统/materials/2026-OS-CH-9-物理内存管理.pdf#page=71|2026-OS-CH-9-物理内存管理, 页面 71]]

**好处：**
- 搜索更快，查询效率更高
- 仅在有必要时加载部分，内存利用率上升

对于64位系统，需要更多层的页表才能避免空间不够用

### 散列页表

散列页表就是把虚拟页号通过哈希函数映射到页表桶中，每个桶用链表保存发生冲突的页表项。查找时先哈希，再在链表中比较虚拟页号，找到后得到物理页框号。它适合虚拟地址空间很大、实际使用页面较少的系统。

- 能解决页表查找慢的问题

### 倒排页表

倒排页表不是为每个进程的每个虚拟页建表项，而是为物理内存中的每个页框建表项，记录这个物理页框当前属于哪个进程、对应哪个虚拟页。它**节省内存，但查找较慢**，所以通常结合哈希表和 TLB 来加速。

> 大致理解：普通页表是以虚拟页号为键，物理页框号为值，通过键查出值；倒排页表是以物理页框号为键，虚拟页号+进程号 为值，通过遍历值（虚拟页号+进程号）来反查其所在的物理页框号
